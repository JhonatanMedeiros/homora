# ADR 0027: Internal monitoring sources for widgets

Status: Accepted — foundation implemented; MON-01 to MON-03 remain separate work.

## Context

Page widgets need the same monitoring facts and state rules as Home, without a connection, extra network capabilities, or access to credentials. Monitor data includes cards and standalone probes. The existing source compatibility rule matches both contract and version. See [ADR 0019](0019-widget-sdk.md), [ADR 0026](0026-widget-modules.md), and [ADR 0024](0024-incidents-and-alert-thresholds.md).

## Decisions

1. **Contract shape.** Three independently versioned, typed contracts in `@homora/widgets`: `homora:monitoring-summary`, `homora:monitoring-problems`, and `homora:monitoring-incidents`, all version 1. They correspond to the three bounded formats, not widget types. The host recognizes only registered exact contract/version pairs. A single open-ended query contract was rejected because the outputs and limits are different. Compiled widget code does not depend on shared, db, integrations, applications or React.
2. **No connection or new column.** The widget definition owns its source; this installation has one internal monitoring source. Page validation requires a null `connectionId` for registered internal contracts, and still requires an existing matching integration connection for integration contracts. The host maps the registered contracts to readers. A per-instance source column or table is unnecessary until multiple internal sources exist. Existing rows are unchanged.
3. **One state classifier.** `monitoringState` is pure and lives in `@homora/widgets`, a package both applications may use. Home's pill and banner call it through their shared summary; the host uses the same function. This avoids a dependency from widgets to shared or either application. Presentation, translations and the existing `isDegraded` used elsewhere remain outside this contract. Tests compare Home and the classifier for the same facts. A backend-only calculation was rejected because the Home already owns live status inputs and its localized presentation.
4. **Read and refresh.** Authenticated GET `/api/widget-sources/monitoring/{summary,problems,incidents}` reads the existing monitor snapshot, settings and incidents, without initiating checks. A strict output schema validates every response. The cache is per query for at most 10 seconds, with at most 32 entries. Lists default to 20 and allow 1–50; incident periods default to 7 days and allow 1–30. Results include `generatedAt` in epoch milliseconds, truncation where applicable, and per-problem `lastAttempt` and `stale`; summary gives a stale count. A check is stale after the larger of 120 seconds or twice its configured interval. Future widgets should refresh at 60 seconds, mark old responses stale if a refresh fails or the response is older than 120 seconds, and isolate each instance's loading/error state. Empty lists are valid, not errors. No connection, new permission, method, header or network access is added.
5. **States.** Summary counts `ok`, `down`, `degraded`, `maintenance`, `blocked`, and `unknown`; a separate flag reports a measurement incident. Maintenance and blocked destinations never count as down; missing observations are unknown. A monitor blocked by policy or masked by a measurement incident is blocked. Problems contain only down and degraded monitors, down first, then monitor ID; the response reports truncation. A stale observation retains its last state and is marked stale, not silently converted to a new observation. Incidents are historical, including open and resolved periods; a maintenance window is not an incident. MON-01 should distinguish each count and missing data; MON-02 should show an empty list, stale markers and truncation; MON-03 should distinguish an empty period, an open incident and truncated results. Final presentation belongs to those issues.
6. **Retention.** Observation history is pruned after 30 days on publication; hourly rollups are pruned after 100 days during rollup. Past maintenance is pruned after 30 days when a window is created, not by a timer. Incident rows have no automatic age pruning (deleting a monitor removes its associated data). The incidents contract limits queries to 30 days; it does not promise that a monitor existed or was observed throughout that period. Incident pruning is deferred: changing history retention requires a separate product decision and migration/operational review.
7. **Privacy.** The current dashboard has one administrator and these endpoints use its existing API session. Outputs contain monitor IDs, names, derived state, timing and latency only; no URLs, credentials, response bodies, maintenance notes, or raw check errors. Names are untrusted display text. Multi-user visibility and authorization must be redesigned with #161 before these results are shared between users. No live infrastructure was contacted in this implementation.
8. **Transfer.** Internal widgets are portable, use null connection IDs and serialize like local widgets, without a source binding. Parser, preview, planner and additive import use the same portability rule. No database migration or transfer format change is needed. The issue described version 3 as current; the checked-out code writes version 6 and reads versions 1–6, including 3. Both behaviors remain unchanged. Connected widgets still require re-creation and are skipped by import.

## Consequences

The contracts provide data only; no MON widget or visual presentation is included. Reader validation failures fail that request without poisoning another reader's cache. Current classification and cache tests are synthetic, not live-service validation. Future work must assess the display, accessibility, stale and failure behavior of each widget independently.
