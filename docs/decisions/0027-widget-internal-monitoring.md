# ADR 0027: Internal monitoring sources for widgets

Status: Accepted — foundation implemented; MON-01 to MON-03 remain separate work.

## Context

Page widgets need the same monitoring facts and state rules as Home, without a connection, extra network capabilities, or access to credentials. Monitor data includes cards and standalone probes. The existing source compatibility rule matches both contract and version. See [ADR 0019](0019-widget-sdk.md), [ADR 0026](0026-widget-modules.md), and [ADR 0024](0024-incidents-and-alert-thresholds.md).

## Decisions

1. **Contract shape.** Three independently versioned, typed contracts in `@homora/widgets`: `homora:monitoring-summary`, `homora:monitoring-problems`, and `homora:monitoring-incidents`, all version 1. They correspond to the three bounded formats, not widget types. The host recognizes only registered exact contract/version pairs. A single open-ended query contract was rejected because the outputs and limits are different. Compiled widget code does not depend on shared, db, integrations, applications or React.
2. **No connection or new column.** The widget definition owns its source; this installation has one internal monitoring source. Page validation requires a null `connectionId` for registered internal contracts, and still requires an existing matching integration connection for integration contracts. The host maps the registered contracts to readers. A per-instance source column or table is unnecessary until multiple internal sources exist. Existing rows are unchanged.
3. **One state classifier.** `monitoringState` is pure and lives in `@homora/widgets`, a package both applications may use. Home's pill and banner call it through their shared summary; the host uses the same function. This avoids a dependency from widgets to shared or either application. Presentation, translations and the existing `isDegraded` used elsewhere remain outside this contract. Tests compare Home and the classifier for the same facts. A backend-only calculation was rejected because the Home already owns live status inputs and its localized presentation.
4. **Read and refresh.** Authenticated GET `/api/widget-sources/monitoring/{summary,problems,incidents}` reads the existing monitor snapshot, settings and incidents, without initiating checks. A strict output schema validates every response. The cache is per query for at most 10 seconds, with at most 32 entries. Lists default to 20 and allow 1–50; incident periods default to 7 days and allow 1–30. Results include `generatedAt` in epoch milliseconds, truncation where applicable, and per-problem `lastAttempt` and `stale`; summary gives a stale count. A check is stale after the larger of 120 seconds or twice its configured interval. Future widgets should refresh at 60 seconds, mark old responses stale if a refresh fails or the response is older than 120 seconds, and isolate each instance's loading/error state. Empty lists are valid, not errors. No connection, new permission, method, header or network access is added.
5. **States.** Summary counts `ok`, `down`, `degraded`, `maintenance`, `blocked`, and `unknown`; a separate flag reports a measurement incident. Maintenance and blocked destinations never count as down; missing observations are unknown. A monitor blocked by policy or masked by a measurement incident is blocked. Problems contain only down and degraded monitors, down first, then known incident start (oldest first), then monitor ID; unknown start times come last within their state. The response reports truncation, total and unmeasured count after the requested scope and degraded filter. A stale observation retains its last state and is marked stale, not silently converted to a new observation. Incidents are historical, including open and resolved periods; a maintenance window is not an incident. MON-01 should distinguish each count and missing data; MON-02 should show an empty list, stale markers and truncation; MON-03 should distinguish an empty period, an open incident and truncated results. Final presentation belongs to those issues.
6. **Retention.** Observation history is pruned after 30 days on publication; hourly rollups are pruned after 100 days during rollup. Past maintenance is pruned after 30 days when a window is created, not by a timer. Incident rows have no automatic age pruning (deleting a monitor removes its associated data). The incidents contract limits queries to 30 days; it does not promise that a monitor existed or was observed throughout that period. Incident pruning is deferred: changing history retention requires a separate product decision and migration/operational review.
7. **Privacy.** The current dashboard has one administrator and these endpoints use its existing API session. Problems additionally expose whether a monitor has a card, a bounded allowlisted monitor reason and an HTTP status; outputs contain monitor IDs, names, derived state, timing and latency; no URLs, credentials, response bodies, maintenance notes, or raw check errors. Names are untrusted display text. Multi-user visibility and authorization must be redesigned with #161 before these results are shared between users. No live infrastructure was contacted in this implementation.
8. **Transfer.** Internal widgets are portable, use null connection IDs and serialize like local widgets, without a source binding. Parser, preview, planner and additive import use the same portability rule. No database migration or transfer format change is needed. The issue described version 3 as current; the checked-out code writes version 6 and reads versions 1–6, including 3. Both behaviors remain unchanged. Connected widgets still require re-creation and are skipped by import.

## Consequences

The monitoring contracts now support page widgets. Reader validation failures fail that request without poisoning another reader's cache. Current classification and cache tests are synthetic, not live-service validation. Future work must assess the display, accessibility, stale and failure behavior of each widget independently.

## Recent incidents widget (#261)

The incidents reader applies the period to overlap (an open incident remains eligible regardless of its start), minimum duration and optional page/group name filters before sorting and limiting. Open incidents sort first, then start and ID descending. Names are used because installation-specific IDs do not survive transfer; a rename requires editing the saved filter. Both selected filter sets intersect. Unfiltered results include standalone probes. A bounded vocabulary and validated HTTP status are the only reason details returned; unknown stored values map to `other`. No response body or raw error is returned.

The widget uses a typed host action to open a monitor: service cards open the existing drawer and standalone probes navigate to probe management. An application import from the widget was rejected to preserve module boundaries. Rows remain separate rather than grouping by service, preserving start and end for each event; truncation is explicit. Long durations use days and hours, rather than unbounded hours. Absolute localized dates avoid ambiguous relative labels. The reader refreshes per instance; an unsuccessful refresh preserves its last good result as stale. The maximum query period remains 30 days and is not a promise of historical coverage.

## MON-02: scope and host actions

The widget stores bounded page and group names, which the host resolves to IDs for the shared monitoring reader. The problems source applies those filters and a latency-degradation switch before sorting, counting and limiting, and counts blocked and unknown monitors in the same scope. Both nonempty filters must match; standalone probes belong to neither and appear only without scope filters. Names, rather than database IDs, preserve meaning across exports; renaming a page or group requires updating the selection. Unknown incident start times sort after known ones and are displayed as unknown. Degradation does not open an incident. The monitor tracks the first check observed above the current latency limit in memory, and the widget labels that time as observed. It orders degraded monitors by that time; after a server restart, the first new observation starts a new observed period, without claiming how long degradation existed earlier. Recovery, maintenance, changed check configuration and a changed threshold reset the period; an old sample reclassified by a new threshold cannot predate the observed threshold change. Inferring earlier onset from retained observations was rejected because the degradation threshold can have changed and its history is not recorded. The response exposes only allowlisted reason codes and numeric HTTP status, never raw errors or bodies. The Home and widget translate the same shared reason key; the widget shows monitor observations, not inferred causes.

A typed host callback opens a card's existing ServiceDrawer or the probe management view for a standalone probe, as the Home popover already does. A direct application import from the widget and a generic navigation URL supplied by the widget were rejected: the host owns navigation and the module does not gain routing access. The frontend source reader validates each response and owns polling and error state per mounted instance; a failed refresh retains the last reading and marks it stale. No source, transport permission, database migration or transfer format was added.

## MON-04: availability contract and widget (#296)

`homora:monitoring-availability` (v1) is added to `monitoringSources` and served by `GET /api/widget-sources/monitoring/availability`, reusing `uptimeSummarizerOf` (`24h`, `7d`, `30d`, minimum 5 counted `up + down` checks). Maintenance, unknown and policy-blocked observations are excluded from both failures and the percentage denominator; when fewer than 5 counted checks exist, `uptimePct` is `null` and the widget reports insufficient data. The widget stores the target's portable name rather than an installation-specific ID, supporting both service cards and standalone probes; missing or renamed targets return `target: null` with HTTP 200 so the widget distinguishes a deleted or renamed target from a source failure. Normal and wide sizes are supported, and failed refreshes retain the last good reading as stale.

## Certificate expiry source (#302)

The version 1 certificate source reads retained TLS observations for service cards, scoped by portable page and group names. A missing selected name prevents matches. It exposes only names, IDs, derived state and expiry/observation times. It uses the current monitor signature, including trust, and never initiates a check. The presentation threshold is independent of monitor policy. A prior or aged observation is marked stale; retention limits historical lookup to 30 days. The existing per-query bounded cache and session authentication apply.
